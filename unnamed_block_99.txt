### 3) Client flows (browser)

**Login (browser)**  
- POST `/api/auth/login` with credentials.  
- Server sets `httpOnly` refresh cookie and returns `accessToken` in JSON.  
- Client stores `accessToken` in memory (never localStorage) and uses `Authorization: Bearer <accessToken>` for API calls.

**Automatic refresh**  
- When access token expires (or on 401), client calls `POST /api/auth/refresh`.  
- Browser sends `httpOnly` refresh cookie automatically.  
- Server rotates refresh token, sets new cookie, and returns new access token.  
- Client replaces in‑memory access token.

**Logout**  
- POST `/api/auth/logout` to clear cookie and remove server record.

**Notes**  
- For WebSocket token issuance, call protected `/api/ws-token` while authenticated (session or access JWT). The issuer should embed `operator.id` and `roles` in the short‑lived WS token payload.

### 4) Revocation and Forced‑Disconnect Integration

- **Revocation**: call `POST /api/auth/revoke-refresh` with `tokenHash` (or raw token) to mark a refresh token revoked. This prevents future refresh and can be combined with `revocationStore` for access JWTs if you track them.  
- **Forced disconnect**: after revoking a refresh token, call your broadcaster’s internal admin endpoint (already implemented) to close active WebSocket sessions tied to the token signature. Use the same deterministic token signature/hash mapping you store in `refreshTokenStore` or the WS token signature.

### 5) Security Checklist and Best Practices

- **Store secrets securely**: `JWT_SECRET`, `SESSION_SECRET`, and any admin secrets must be in a vault.  
- **Use HTTPS/WSS** in production; set `secure: true` on cookies.  
- **Short access TTLs** (e.g., 5 minutes) and rotate refresh tokens on every use.  
- **Persist refresh tokens server‑side** (Redis or DB) and store only hashed values if you must persist raw tokens. The example stores raw token hashes.  
- **Revoke on suspicious activity**: revoke refresh tokens and force disconnect active sessions immediately.  
- **Protect revoke endpoints** with `requireRole('admin')`.  
- **Audit**: record login, refresh, rotation, revoke, and logout events to Jetweb lineage with canonical JSON.  
- **Rate limit** login and refresh endpoints to mitigate brute force and replay attempts.  
- **CSRF**: using httpOnly cookies for refresh tokens requires CSRF protection on state‑changing endpoints; keep refresh endpoint POST and consider sameSite cookie policy. For extra safety, require a double submit CSRF token for refresh in high‑risk deployments.
